# StreamForge Requirements

## Purpose

StreamForge will demonstrate reliable ingestion, asynchronous processing, and analysis of IoT telemetry. This document defines the intended MVP behavior; it does not claim that the behavior is implemented in M1.

## MVP Scope

The sole initial domain is **IoT Telemetry & Device Monitoring**. The MVP is expected to:

1. Accept versioned `telemetry.reading` events through an authenticated write API.
2. Durably record newly accepted events and return HTTP `202 Accepted`.
3. Treat identical retries of the same event as idempotent.
4. Reject reuse of an event ID with conflicting content.
5. Publish accepted events asynchronously through Kafka using a transactional outbox.
6. Process deliveries at least once while making business effects idempotent.
7. Persist telemetry-derived state and expose read-only query APIs.
8. Show device status, recent readings, and processing state in a demo UI.
9. Provide authorized operational controls for later replay and failure-injection exercises.
10. Expose enough health, logs, and metrics to understand normal and degraded behavior.

The exact endpoints, persistence schema, conflict status code, canonical equality rules, replay protocol, derived analytics, and status model remain subject to M3 design review.

## Functional Requirements

### Ingestion

- The API shall validate the event envelope and measurement fields against the supported contract version.
- A valid new event shall become durably accepted before the API returns HTTP `202`.
- The API shall generate `receivedAt`; clients shall not control it.
- An identical retry shall not create duplicate business effects.
- Reusing an `eventId` for materially different content shall be rejected and recorded observably.
- Unsupported event types or schema versions shall fail explicitly rather than be silently interpreted.

### Asynchronous Processing

- Accepted events shall be made available to Kafka without relying on an unsafe database/Kafka dual write.
- The Worker shall tolerate duplicate delivery.
- Processing success and failure shall be observable.
- Poison-event handling, retry limits, dead-letter behavior, and replay controls shall be specified before implementation.
- `processedAt` shall be generated by the processing system after successful processing under the final M3 definition.

### Query and Demonstration

- Read APIs shall provide useful device-oriented telemetry views.
- The UI shall distinguish acceptance from processing completion.
- Public demo access, if enabled, shall be read-only.
- Write, replay, failure-injection, and administrative controls shall require server-side authorization.

### Operations

- API and Worker shall be independently runnable and observable.
- Health checks shall distinguish application availability from dependency readiness where practical.
- Operators shall be able to correlate an event by stable `eventId` across API, outbox, Kafka, Worker, and persistence logs.

## Non-Functional Requirements

### Reliability and Data Integrity

- Delivery semantics are **at least once**, not end-to-end exactly once.
- Business effects shall be idempotent under duplicate requests, outbox publication retries, Kafka redelivery, and Worker restart.
- A committed accepted event shall not depend on Kafka being available at request time.
- PostgreSQL is the primary operational and initial analytics database.
- Transaction and retry behavior shall be tested under representative failure modes before release.

No numeric availability, latency, throughput, retention, recovery-time, or recovery-point objective is approved in M1. These must be measured and agreed rather than invented.

### Security

- Kafka and PostgreSQL shall not be publicly reachable.
- Authorization shall be enforced server-side.
- Secrets shall not be committed to the repository.
- Input validation, dependency scanning, least privilege, secure transport, and auditable control operations are required before public deployment.
- The security model and identity provider remain open decisions.

### Maintainability

- The system shall begin as a modular codebase with clear ownership boundaries.
- API and Worker shall be separate processes without premature microservice decomposition.
- Event contracts shall be versioned and backward-compatibility behavior documented.
- Development and verification commands shall be reproducible through repository-owned wrappers and configuration.

### Portability and Cost

- Local development shall not require AWS.
- AWS is a final deployment goal, not an M1 deliverable.
- EC2 plus Docker Compose is only a preferred candidate until M8 evaluates cost, security, operability, and host resources.

## Primary User Journeys

### Device or Producer Submits a Reading

1. An authorized producer sends a V1 reading with a UUID event ID.
2. The API validates and attempts durable acceptance.
3. A new event receives `202 Accepted`; acceptance does not mean processing has completed.
4. The outbox publisher later sends the event to Kafka.
5. The Worker processes it and updates queryable state.

### Producer Retries

1. A producer retries after a timeout using the same event ID and content.
2. The API recognizes the existing event.
3. No duplicate durable event or business effect is created.
4. The response semantics for a known identical event will be finalized in M3.

### Conflicting Event ID

1. A producer submits an existing event ID with different material content.
2. The API rejects the request.
3. The conflict is observable; the precise HTTP status and audit representation remain open until M3.

### Viewer Inspects Device State

1. A viewer opens the read-only UI or read API.
2. The system returns device telemetry and clearly identifies stale, accepted, processing, failed, or processed state where supported.
3. Public viewers cannot invoke control operations.

### Authorized Operator Investigates Failure

1. An operator correlates records by event ID and inspects health, logs, and metrics.
2. If approved and implemented, the operator uses protected replay or failure-injection controls.
3. Reprocessing preserves idempotent business effects and leaves an audit trail.

## Explicit Exclusions

- Domains other than IoT telemetry and device monitoring.
- Python services before M6 unless separately justified and approved.
- S3/Parquet storage before M6 reconsideration.
- Premature service decomposition or additional deployment units.
- Multi-node production Kafka in the initial local foundation.
- End-to-end exactly-once claims.
- Public write or administrative access.
- AWS deployment before M8 evaluation and explicit approval.
- Business functionality, source modules, dependencies, infrastructure, or deployment in M1.

## Acceptance Principles

- Documentation and implementation must agree on contract and delivery semantics.
- Acceptance, publication, and processing are separate states.
- Durable state changes define success; logs alone do not.
- Every reliability claim needs a testable failure scenario.
- Unresolved details remain explicit until the responsible milestone reviews them.
- Milestone completion requires independent review and user approval.
