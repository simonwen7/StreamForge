# M4 — Asynchronous Event Processing

## Objective

Move an accepted telemetry event from the outbox to Kafka, then record one durable processing receipt. Do not claim exactly-once delivery or single-broker durability.

## Status

**Accepted by the owner**

The owner marked M4 completed. Local M4 verification passed before that acceptance. This implementation pass did not independently inspect the remote GitHub Actions run. M4 is not a production deployment.

## What M4 implements

- Apache Kafka 4.2.1, single-node KRaft, in `infra/compose.yaml`
- Topics `telemetry.reading.v1` and `telemetry.reading.v1.dlt`, one partition and replication factor 1
- An outbox publisher inside the API, disabled unless `OUTBOX_PUBLISHER_ENABLED=true`
- An independent `backend/worker` process
- Flyway `V3__create_processed_events.sql`
- `GET /api/v1/telemetry/readings/{eventId}` reports `PUBLISHED` from `published_at` and `PROCESSED` from a processing receipt

HTTP 202 is unchanged. It means the event and outbox row committed.

## Kafka listeners

| Listener | Address | Host publish |
| --- | --- | --- |
| Internal client | `kafka:9092` | Not published |
| Host client | `127.0.0.1:9094` | `127.0.0.1:9094` only |
| Controller | `kafka:9093` | Not published |

The image is `apache/kafka:4.2.1` pinned by digest `sha256:9916d60eca5d599550e2c320230808fda342124ba550bb4ac4ea8591803262a0`. The registry index contains linux/amd64 and linux/arm64. Broker data uses the named volume `streamforge-kafka`. Local retention is 168 hours. The heap is capped at 512 MB. Clients use PLAINTEXT. That is a local-development limitation, not a production security design.

A Kafka acknowledgement means the single broker accepted the record. It does not mean the Worker committed a receipt. Disk loss or expired retention can drop broker data.

## Publisher

`OUTBOX_PUBLISHER_ENABLED` defaults to false. No scheduled publication runs, and historical pending rows stay pending. HTTP ingestion does not call Kafka.

When the flag is true, one API process polls the oldest pending rows, 50 at a time, about once a second. It sends `acks=all`, waits for the acknowledgement, and only then sets `status=published` and `published_at`. A failed or uncertain send leaves the row pending. The publisher does not use `failed` as a terminal state.

Enabling the publisher also publishes pending rows that were already in the database. The preserved development database has pending M3 events. Leave the flag false there.

M4 supports one enabled publisher. A second API process with the flag true can publish duplicates. There is no lease. A crash after the broker acknowledgement and before the SQL update publishes the record again on the next poll. Producer idempotence does not close that restart window.

## Worker

Start PostgreSQL, Kafka, and the API migration before the Worker. The Worker does not run Flyway and does not open an HTTP port. Its runnable archive is the `exec` classifier jar, so the plain jar can be used on a test classpath without pulling in the API.

It joins `streamforge-telemetry-worker`, reads `telemetry.reading.v1`, and uses manual acknowledgement. Automatic offset commits are off. For a valid record it compares the key, `event-id` header, and payload with the stored telemetry row, then inserts one `processed_events` row. A duplicate delivery finds the primary key and does not insert another row. The offset is acknowledged after that transaction commits.

These records are poison and are dead-lettered after Kafka accepts the dead-letter record:

- malformed JSON
- unsupported schema version or event type
- a key or `event-id` header that does not match the payload
- a missing stored event
- a stored event whose fields do not match the record
- a foreign-key violation while inserting the receipt

PostgreSQL connection failures, pool exhaustion, and recoverable database timeouts stay on the main topic. The retry interval is five seconds. They are not dead-lettered. M5 owns richer retry orchestration.

If the dead-letter send fails or times out, the source record is not acknowledged. A crash after a successful dead-letter send and before the source acknowledgement can copy that dead-letter record again. The dead-letter topic is isolation, not replay.

## Startup order

1. PostgreSQL and Kafka, including topic creation.
2. API, so Flyway applies V3. Keep the publisher disabled unless publication is intended.
3. One Worker.

`/actuator/health` does not require Kafka. A broker outage must not turn that endpoint DOWN while PostgreSQL and the API are healthy, and it must not fail the ingestion transaction.

## Tests executed locally

`./mvnw -B -ntp verify` includes the M2 and M3 suites plus publisher, Worker, dead-letter, Kafka-outage, and HTTP-to-receipt tests on disposable PostgreSQL and Kafka containers. Remote CI is not verified until the user pushes.

## Remaining limitations

- One publisher, no leases, and no terminal publication failure state
- One broker, replication factor 1, and PLAINTEXT
- No dead-letter replay, analytics read model, or multi-publisher safety test
- The automated suite does not restart a broker. A separate local run, on a disposable database, accepted HTTP 202 while Kafka was stopped and published that row after the broker returned. The preserved database was not used for that run.
- R-13 and R-15 remain gates before any non-loopback exposure
