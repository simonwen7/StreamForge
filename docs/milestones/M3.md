# M3 — Event Sources & Ingestion

## Objective

Accept versioned telemetry from a known device, store the event and one outbox row atomically, and make retries safe. Do not publish to Kafka or process the event.

## What M3 implements

- `POST /api/v1/devices`, `GET /api/v1/devices/{deviceId}`, and `GET /api/v1/devices` for the device-admin API key
- `POST /api/v1/telemetry/readings` and `GET /api/v1/telemetry/readings/{eventId}` for the ingestion API key
- Nested `telemetry.reading` schema version 1
- Canonical SHA-256 identity and concurrency-safe idempotency
- Flyway `V2__create_ingestion_tables.sql` for `devices`, `telemetry_events`, and `outbox_events`
- A Java CLI simulator that sends real HTTP requests

HTTP `202` means the event and outbox row committed. `publication` is `PENDING` and `processing` is `NOT_STARTED`.

## Authentication

Two environment variables supply the credentials:

- `DEVICE_ADMIN_API_KEY` for device routes
- `INGESTION_API_KEY` for telemetry routes

Send `Authorization: Bearer <key>`. The keys must be different and at least 32 characters. Startup rejects missing, blank, short, identical, or unresolved values. Health remains anonymous. Every other route requires authentication, and an authenticated caller still cannot reach a route that was not explicitly allowed.

CSRF protection is disabled because the API does not use cookies. A browser does not attach a bearer header automatically. CORS is disabled, so the API does not opt browsers into cross-origin calls. These choices fit a loopback CLI and server-side caller. They are not a public-browser security design. Two static keys are not user identity, rotation, or rate limiting.

## Database

V1 is unchanged. Its checksum remains `595439424`. V2 adds the ingestion tables in schema `streamforge` and leaves `schema_info` in place. The outbox allows `pending`, `published`, and `failed`, with `published_at` null for pending rows, so M4 can record publication without replacing the check. M3 only inserts `pending`.

Acceptance uses one Spring transaction and `INSERT ... ON CONFLICT DO NOTHING`. PostgreSQL uniqueness decides the race. The isolation level is READ COMMITTED.

## Simulator

The simulator is a separate Maven module, `backend/simulator`, so it is not part of the API process. It uses `java.net.http.HttpClient`. It reads `INGESTION_API_KEY` from the environment and does not print it. Count is limited to 100 events per invocation.

```bash
export JAVA_HOME="$(/usr/libexec/java_home -v 21)"
set -a && source infra/.env && set +a
java -jar backend/simulator/target/streamforge-simulator-0.1.0-SNAPSHOT.jar \
  --base-url http://127.0.0.1:8080 \
  --device-id sensor-042 \
  --seed 7 \
  --count 2 \
  --interval-ms 0 \
  --mode valid
```

The device must already exist. `--mode` is `valid`, `duplicate`, `conflict`, `invalid-flat`, or `invalid-future`. The same seed produces the same events, and repeating that seed is safe.

`valid` succeeds when each event returns 202 (newly accepted) or 200 (already accepted). A 409 in this mode is a failure. `duplicate` succeeds for 202 followed by 200, or for 200 on every request when the event was already stored. Later responses stay 200. `conflict` succeeds when the baseline returns 202 or 200 and each changed submission returns 409. A conflicting submission that returns 200 or 202 fails. The base URL must be loopback. M3 is not accepted.

## Remaining limitations

- No Kafka publisher, Worker, replay, analytics, or frontend
- No device update or delete
- Late events are stored; no lateness policy is applied
- No rate limiting, credential rotation, or HTTPS termination
- Local API and PostgreSQL binds stay on loopback
- A foreign-key failure after the device check, which M3 cannot cause through its API because devices are not deleted, would roll back and return 503 rather than 404
- R-13 remains critical for any exposure beyond this local setup
