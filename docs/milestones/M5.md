# M5 — Data Correctness & Reliability

## Objective

Make the M4 outbox and Worker safe under concurrent publishers, redelivery, and temporary dependency failures. Do not claim exactly-once Kafka delivery.

## Status

**Pending Final Check / User Acceptance**

M5 is implemented and locally tested. It is not accepted. Remote GitHub Actions for M5 is not verified.

## What M5 implements

- One outbox claim at a time, with `FOR UPDATE SKIP LOCKED` and a UUID `claim_token`
- A 30-second lease, renewed by the fenced pre-send update. A cycle handles at most 20 events
- `attempt_count` increments only when a Kafka send is about to start
- Exponential backoff with jitter for transient failures. Those rows stay `pending` after 20 attempts
- `failed` only for a non-retryable encoding or record defect, with the event retained
- `GET` publication values `PENDING`, `PUBLISHED`, and `FAILED`
- Worker SQLState classification and dead-letter headers without a stack trace
- Rejection of duplicate JSON object keys on HTTP ingestion and in the Worker
- Flyway `V4__outbox_claim_and_retry.sql`

The publisher stays off unless `OUTBOX_PUBLISHER_ENABLED=true`. Enabling it publishes historical pending rows, including preserved M3 events. Leave the flag false on that database unless those rows should be published.

## Claim and retry

An eligible row is `pending`, due on `next_attempt_at`, and has no unexpired lease. The claim statement commits before any Kafka call. The pre-send update must still match `claim_token`. A zero-row update means the publisher lost ownership and must stop acting on that token.

A crash after the broker acknowledgement and before the fenced publish update can send the record again. A crash after `attempt_count` increases and before the send still counts as an attempt. Producer idempotence does not close either window.

Transient codes include `KAFKA_TIMEOUT`, `KAFKA_SEND`, and `DATABASE_UPDATE`. The due time is `clock_timestamp()` plus the delay. The base delay is 1 second, the cap is 5 minutes, and jitter is about ±20 percent.

`CONTRACT_ENCODING` is permanent. It covers a stored field that cannot be embedded in the JSON contract, or a Kafka record that the producer rejects as too large or not serializable. Uncertain acknowledgement stays retryable.

## Operator requeue

There is no HTTP requeue route. After the underlying defect is corrected, this statement restores one failed row. It does not insert a second outbox row and it does not change a published row:

```sql
UPDATE streamforge.outbox_events
SET status = 'pending',
    claim_token = NULL,
    claimed_until = NULL,
    next_attempt_at = NULL,
    last_error_code = NULL,
    attempt_count = 0
WHERE event_id = '<event-id>'::uuid
  AND status = 'failed'
  AND published_at IS NULL;
```

Do not run it against the preserved development database unless that event should be published.

## Worker

Connection failures, deadlocks, and other non-constraint database errors stay on `telemetry.reading.v1`. SQLStates `23503`, `23502`, and `23514` are poison. SQLState `23505` is success when the receipt already exists, and poison otherwise. The receipt insert still uses `ON CONFLICT DO NOTHING`. The offset is acknowledged only after the receipt transaction commits, or after Kafka confirms the dead-letter record.

Dead-letter headers keep the original topic, the exception type, the cause type, and a short message. They do not include the stack trace.

Duplicate JSON keys produce HTTP 400 and no accepted row. The Worker dead-letters them.

## Diagnostics

About once a minute, while work remains, the publisher logs pending, eligible, active claim, expired claim, and failed counts, plus the age of the oldest pending row. Every 20th publication attempt logs that the event is still retryable. Logs use `eventId` and the error code. They do not include API keys or database passwords.

## Limits

- One Kafka broker, replication factor 1, and PLAINTEXT
- An overlapping send after lease expiry can duplicate a Kafka record
- No replay tool, analytics pipeline, or public deployment
- R-13, R-15, and R-27 remain open
